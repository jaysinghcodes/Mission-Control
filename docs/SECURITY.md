# Security

Read this before you open a port. The short note on the README is the same rule: login is required off loopback, and tunnel port 3011 is never treated as the owner. Laptop steps are in [REMOTE.md](REMOTE.md).

* Dashboard login replaced the old rule that every write needed `x-ingest-token`. That rule was issue 36. Agent ingest still uses the header. The dashboard uses a session cookie.
* When the real socket address is loopback (`127.0.0.1` or `::1`), dashboard reads and writes stay open, including `GET /sessions` and `GET /health`. `npm run dev` is this case: Vite proxies from `127.0.0.1`.
* When the socket address is not loopback, every dashboard read and write returns 401 until `POST /auth/login` sets the `mc_session` cookie. `GET /auth/session`, `POST /auth/login`, and `POST /auth/logout` stay open so the browser can sign in.
* `POST /auth/logout` clears the cookie. When the caller is loopback or holds a valid session, it also bumps a session version stored on disk. A cookie copied before that logout returns 401, including after a restart. `POST /auth/password` stores a new hash and bumps the same version, so a password change revokes every session. Open sockets that are not loopback are disconnected. Settings includes Revoke sessions, which calls logout.
* Wrong passwords are limited per client IP. The defaults are 5 failures, a 60 second window, and a wait that starts at 60 seconds and doubles up to 15 minutes (`LOGIN_FAIL_LIMIT`, `LOGIN_WINDOW_SECONDS`, `LOGIN_BACKOFF_MAX_SECONDS`). The next try is HTTP 429 with a `Retry-After` header, even when the password is right. The sign in page shows the message from the API. Off Compose that is "Too many tries. Try again in a minute. npm run login:reset clears the lock." When `MC_COMPOSE` is `1` the message names `docker compose exec api npm run login:reset`. Loopback is not limited. Agent ingest with `x-ingest-token` is not limited. `npm run login:reset` clears every lock. Under Compose, `docker compose exec api npm run login:reset` runs that command in the api container. Restarting the API clears the lock too. The session version does not reset.
* The local nginx listener sets `X-Real-IP` and `X-Forwarded-For` from the address it accepted and drops any copy the client sent. It also clears `X-MC-Remote`. The API trusts those client headers when that peer is the web service on the Compose network (`BUNDLED_PROXY`, default `web`, resolved from the compose service name) or when the peer is listed in `TRUSTED_PROXY`. Trusting the header picks the login bucket. It does not grant loopback and it does not skip login. Any other peer is counted by its socket address, so a spoofed header on the API port is ignored. Leave `TRUSTED_PROXY` unset for Compose. Do not set it to the Docker bridge.
* nginx listens on a second port for Cloudflare Tunnel and Tailscale Serve. The host port is `MC_REMOTE_PORT` (default 3011), published on `127.0.0.1` only. That listener always sets `X-MC-Remote` to `1` and passes `CF-Connecting-IP` and `X-Forwarded-For` from the tunnel. The API trusts that tag only from the bundled nginx. On that port nobody is loopback and nobody is the owner. The bucket is `CF-Connecting-IP` when it is an IP, otherwise the first `X-Forwarded-For` hop (Tailscale Serve sends the client there). With neither header, every such request shares one remote bucket. That bucket is not the owner bucket. SSH tunnels use the local web port only. The laptop steps are in [REMOTE.md](REMOTE.md). On a tunnel other than Cloudflare, a new spoofed `CF-Connecting-IP` on each try is a new bucket.
* Compose sets `HOST=0.0.0.0` inside the api container. nginx talks to `api:3000` on the Docker network, so the socket is the web container, not `127.0.0.1`. A browser on the host still has to sign in. The published host ports stay on `127.0.0.1`. A host `curl` to the API port is not loopback. It shares the owner lock with the browser on the local web port, and it does not share a tunnel client's lock.
* `bash install.sh` stores `DASHBOARD_PASSWORD_HASH` (scrypt) and `SESSION_SECRET`. The password is in the final summary, once, on the first install. A second run does not print or replace them. `npm run password:reset` writes a new hash to the session file, prints the password once, and revokes every session. It prints that password only after the new hash is read back. There is no HTTP route for that reset. Under Compose run `docker compose exec api npm run password:reset`. `bash install.sh` sets `MC_INSTALL_MODE=compose` in `.env`, and a host `npm run password:reset` runs inside the api container and does not write a host file. If the api is not running, or Docker cannot run that command, it exits nonzero and tells you to run `docker compose up -d` first. With no hash, loopback stays open and logs a warning. With no hash or no session secret on any other bind, the API refuses to start.
* When `INGEST_TOKEN` is set, agent ingest requires header `x-ingest-token`: `POST /events`, `POST /agents/register`, `POST /agents/:id/heartbeat`, `POST /runs`, and `PATCH /runs/:id`. A missing or wrong token is 401 JSON `{"statusCode":401,"message":"unauthorized"}`. A session cookie does not replace that header.
* With no `INGEST_TOKEN` and `HOST` on loopback, ingest stays open outside production and the API logs one warning. With `NODE_ENV=production` and no `INGEST_TOKEN`, ingest returns 401 even on loopback. Dashboard loopback writes stay open.
* With no `INGEST_TOKEN` and `HOST` on any other address, the API refuses to start. Set `INGEST_TOKEN` to a long random string (`openssl rand -hex 24`) and start again. Compose does not fall back to a dev token.
* The web bundle contains no ingest token and no socket token. Vite and nginx do not attach `x-ingest-token`. The browser sends the session cookie. `npm run seed:demo` writes through Prisma and does not send the header. The bridge still posts `POST /events` with the header.
* `npm run dev` binds `127.0.0.1` (`HOST` in the root `.env`). Compose publishes the API on `127.0.0.1` as well. Publishing `0.0.0.0` without a dashboard password is refused at startup.
* `POST /agents/register` adds one bot without replacing the roster. `agents.snapshot` removes only snapshot rows that the payload omits. Default and registered bots stay. A registered bot with no heartbeat for 10 minutes reads `online: false` and is not deleted. The screen shows Offline and dims the idle robot. Unclaimed sample bots hide once a real bot exists until Show sample bots is on.
